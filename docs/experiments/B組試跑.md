# B 組兩次實驗分析

## 1. 實驗設定與可比性

兩份結果中可核對的主要模擬設定相同：模擬 seed 42、40 名人口、一次乾旱、穩定期 5 天、乾旱期 8 天、評估期 8 天，乾旱期間產出倍率 0.2。政府皆使用 LLM 並開啟記憶，社會規則皆為 `record` 模式，使用 `rules/v0.yaml`。History 未保存完整執行 metadata，因此未記錄的執行參數不能假定相同。

兩次使用相同的模型名稱，但 History 的執行紀錄沒有保存 LLM seed、temperature、Provider API 或 commit；因此無法確認這些執行條件與 Seed 42 完全相同，也不能把結果差異視為只由 Prompt 版本造成。

| 項目 | 實驗一：History | 實驗二：Seed 42 |
|---|---|---|
| 結果位置 | `runs/group_b/history/` | `runs/group_b/seed42/` |
| 模擬 seed | 42 | 42 |
| 模型 | `Qwen/Qwen2.5-7B-Instruct` | `Qwen/Qwen2.5-7B-Instruct` |
| Prompt 版本 | `gov-v3` | `gov-v6` |
| LLM seed | 未記錄 | 45 |
| Temperature | 未記錄 | 0.0 |
| Provider／API | 未記錄 | Modal；API URL 見 `meta.json` |
| Git commit／狀態 | 未記錄 | `89dffdb813a8864fc4018c3d32685a7abd45a5c9`；`dirty = true` |

兩次都只跑一次天災，因此可以觀察災害決策與記憶生成，不能驗證政府是否在後續天災中運用記憶。

### 政府行動

### 發現

政府先設定糧價上限；Tick 5 發糧給 dependent，之後多次指定向 `consumer` 發糧。評估期價格由 46.4014 降至 5.1046，但仍高於均衡區間；發糧總量 24，全期累計 92 挨餓人天。

發糧資格判斷是「居民正在挨餓」且「類型符合」。政府觀察到挨餓總人數及居民類型，沒有各類型的挨餓人數，因此無法據此判斷應指定哪一類型；拒絕結果本身不足以證明篩選程式有錯。

政府收到「沒有符合條件的平民」後，仍在 Tick 8–11、15–17 連續提出相同參數的發糧決策，並在 Tick 19–20 再次提出。拒絕理由會進入後續 prompt；遭拒後會重新呼叫 LLM，這些不是 replay。這是待團隊判斷的治理行為，不宜只歸類為資格不符。

### 記憶品質

Tick 20 更新為 version 1，但記憶和事件紀錄有三處不一致：

1. 漏記 Tick 13 成功發糧 1 單位。
2. 將 Tick 14 成功發糧 6 單位誤記為失敗。
3. 宣稱糧價已穩定在合理水平、價格上限有效防止漲價；但評估期價格仍高於均衡區間。

因此，這份記憶有事件遺漏、結果誤記及政策效果誤判，不能直接視為正確的治理經驗。

### 結果

| Tick 20 糧價 | 2.7628，仍高於均衡區間 |
| 恢復結果 | 失敗 |
| 評估期價格上限 | 6／8 天生效 |

### 政府行動

| 行動 | 次數 | Tick／內容 |
|---|---:|---|
| 現金補助 `cash_transfer` | 8 | Tick 3、5–7、9–11、14；成功 3 次、遭拒 5 次 |
| 設定糧價上限 `price_cap` | 6 | Tick 4、8、12–13、16、19；上限 4，持續 3 天 |
| 暫不行動 `idle` | 3 | Tick 15、17–18；Tick 18 為 replay |

| Tick | 補助結果 | 受助人數 | 金額 |
|---:|---|---:|---:|
| 3 | 成功 | 20 | 20 |
| 5–7、9–10 | 遭拒 | — | — |
| 11 | 成功 | 1 | 1 |
| 14 | 成功 | 8 | 8 |

三次成功補助合計 29 人次、金額 29。五次遭拒的 `replayed` 均為 `false`，拒絕理由均為「沒有符合條件的平民」。

### 發現

政府 Tick 3 先向全體 `consumer` 發放現金補助，之後改為只補助挨餓的 `consumer`。Tick 5–7 連續三次遭拒，Tick 9–10 又以相同參數提出補助；Tick 11 有符合條件者後，補助成功。遭拒決策均為 LLM 重新提出，不是 replay。

政府只看得到挨餓總人數及居民類型，無法掌握各類型的挨餓人數。這可能使補助對象與實際挨餓者不匹配；目前不能確認各類型挨餓人數分布，也沒有證據顯示資格判斷程式出錯。

評估期有 6／8 天價格受上限影響，不能把這些天的價格當成未受干預的自然恢復。Tick 20 價格仍為 2.7628，高於均衡區間；挨餓人數最高 13 人，期末仍有 5 人挨餓，累計 118 挨餓人天。價格下降與挨餓人數減少同時發生，但不能僅憑這些指標把改善完全歸因於價格上限或現金補助。

### 記憶品質

Tick 20 更新為 version 1。程式寫入的災害紀錄正確包含失敗、118 挨餓人天、死亡 0 人、最高價 8.35、評估期 6／8 天價格受上限影響，以及各類決策次數。

LLM 教訓部分將 `cash_transfer` 概括為沒有有效幫助平民，未保留 Tick 3、11、14 三次成功補助的人數與金額，也未分析補助前後挨餓人數變化。因此，災害摘要資料正確，但政策效果分析過度概括，沒有區分成功與遭拒案例。

Seed 42 的 `llm_calls.jsonl` 共 22 筆紀錄，均標示 `prompt_version = gov-v6`，與 `meta.json` 相符。

## 4. 兩次實驗比較

| 比較項目 | 實驗一：History（gov-v3） | 實驗二：Seed 42（gov-v6） |
|---|---:|---:|
| 最高糧價 | 46.4014 | 8.3457 |
| Tick 20 糧價 | 5.1046 | 2.7628 |
| 挨餓人天 | 92 | 118 |
| 死亡 | 0 | 0 |
| 評估期價格上限天數 | 0 | 6／8 |
| 主要救濟 | 發糧 5 次成功、9 次遭拒 | 現金補助 3 次成功、5 次遭拒 |
| 記憶主要問題 | 漏記、誤記事件，並錯判價格已恢復 | 災害摘要數據正確，但成功補助案例及效果分析不足 |
| 天災恢復 | 失敗 | 失敗 |

兩次都出現遭拒後重複提出相同或高度相似救濟決策的情況，也都未在評估期恢復至均衡價格區間；兩次死亡均為 0。這種重複決策可列為待團隊討論的候選行為，不代表已被現行社會規則判定違規。

**候選 Don't：**同一決策因相同理由遭拒後，在相關條件未改變前，不得原樣重送。是否納入 `rules/v0.yaml`，由團隊依行為標準討論決定。

**總結：**gov-v6 這次的最高價及 Tick 20 價格低於 gov-v3，但挨餓人天較高；不能據此判定 gov-v6 全面較好或較差。兩次結果受到多項政策行為影響，且 History 未保存 commit、LLM seed 等執行資訊，Seed 42 則記錄 `dirty = true`，所以不能把差異單獨歸因於 Prompt 版本，也無法完全重現 History 實驗。
