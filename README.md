# Multi-Agent 文明模擬器（後端）

研究「AI Agent(政府) 面對天災時會如何決策」。 AI 政府治理一群規則式平民，社會經歷 N 次天災；觀察政府的決策，以及每次天災後的固定時間內，市場均衡價格會到多少。

此 repo 是僅負責後端(模擬引擎、Agent、world-api等) 。前端介面在：
[tpi_frontend](https://github.com/TPIBBB/tpi_frontend)。

# 研究問題(目標)

每次天災發生後，在固定的時間段（評估期）內，市場均衡價格會到多少？經歷多次天災後，這個結果會如何變化？

每次天災的評估期長度都相同，結果才能互相比較。

# 模擬設計

# 角色

| 角色 | 控制方式 | 說明 |
|---|---|---|
| 政府 | AI Agent（LLM） | 天災發生時做出決策 (主要觀察對象) |
| 平民 | Rule-based Agent | 依固定規則工作、交易，對政府決策與市場變化做出反應 (職業、階級等待定) |

# 實驗流程

```
社會正常運作 → 天災發生 → 政府決策 → 引擎驗證並結算 → 記錄評估期內的均衡價格與決策內容
      ▲                                                     │
      └──────── 更新政府記憶、視情況新增社會規則 ◄──────────┘
```

# 系統架構

```
前端 ─────┐
          ├→ digiRunner（API Gateway）→ world-api（FastAPI）→   模擬引擎
Agent 端 ─┘
```

- **模擬引擎**：推進回合、觸發天災，驗證決策並更新世界狀態。(AI 政府提出決策後，結果由引擎依固定規則計算，避免 LLM 憑空創造資源，不同實驗用同一套規則進行比較)
- **world-api**：模擬引擎對外的 HTTP 介面，前端與 Agent 透過它查詢世界狀態、送出行動。
- **digiRunner**：管理前端與 Agent 對 world-api 的呼叫。

詳細設計見 [docs/architecture.md](docs/architecture.md)。

# 記憶

政府的記憶存成 Markdown 檔。經歷幾次天災後，如果政府有新的發現，可修改這份記憶，並帶著它面對下一次天災。藉此觀察政府是否真的會從過去的天災中學習。

# 社會規則

社會規則有明確的 do and don't，例如：

- 不能亂殺平民
- 不能隨意發行貨幣

規則不會一開始就全部訂好。先觀察前幾次天災中，政府是否做出違反社會邏輯的決策，再把需要的規則加上去。

# 實驗設計(還沒討論)

僅觀察 AI 政府，無法確定均衡價格的變化是因為政府決策，還是天災較輕、市場自行恢復或運氣好，需要分組別進行比較。

| 組別 | 政府 | 記憶 | 社會規則 | 用途 |
|---|---|---|---|---|
| A 沒有記憶 | AI Agent | 無 | 無 | 當對照組 |
| B 有記憶(沒有社會規則) | AI Agent |有 | 無 | 看在無規則下政府會不會為了達成目標而亂搞 |
| C 有記憶(有社會規則) | AI Agent | 有 | 有 | 看政府是否能意識到為何會成功(？) |

**固定不變的條件**：除了表中的變因，各組使用相同的初始世界、平民設定、引擎規則、prompt 版本，以及相同的天災時間表與強度。

**重複次數**：每組用同一批 seed 各跑多次，比較平均與差異。LLM 每次的回答可能不同，只跑一次的結果可能只是運氣。

**暫定**：一次模擬經歷 10 次天災，每組 5 個 seed；回合數由天災各段長度推算（需先估算 LLM 費用）。

# 公民細節

- 特性：有無買賣、有無產出 (4種)
(有產出的人產量隨機)
- persona：會不會遵守政府政策、sloth、greed、risk tolerance、gluttony (七宗罪)

# 設計決定

完整內容見 [docs/architecture.md](docs/architecture.md)。

- **研究目標**：只看市場均衡價格；每次天災都設固定長度的評估期，觀察評估期內均衡價格會到多少
- **政府可以做哪些決策**：封閉清單，包含穩定、財政、強制、發布預報四類，刻意納入可能違規的行動
- **違規決策的處理**：引擎拒絕，並把拒絕理由回饋給政府
- **記憶更新的時機**：每次天災評估期結束都可以更新，政府可選擇不更新；記憶不跨 run
- **實驗的比較方式**：規則集在 run 內固定、有版本號；每個 run 有 manifest 記錄所有版本
- **範圍**：平民維持 rule-based；移除舊方向的資訊權限機制；實驗中政府經由 digiRunner 呼叫 world-api

# 要討論的

- **實驗方式**：要比較n次看成功幾次/總共經歷到第幾次會成功
- **均衡價格的定義**：目前引擎只有依淨需求調整的市價，沒有計算均衡價格，需要決定怎麼計算或判定；評估期結束時價格還沒穩定要怎麼記錄
- **看哪個商品**：市場有 food、wood、tools，天災只讓糧食減產，要只看 food，還是全部都看
- **評估期的起點**：從天災開始還是結束起算（架構文件目前排在天災結束後）
- **怎樣算結果好**：要跟天災前的價格比，還是跟 A 組比；是否需要達標門檻。沒有標準就無法判斷政府有沒有比不介入更好、有沒有從記憶學習，「第 k 次天災的達標比例」也無法計算
- **政府知道的目標**：政府的 prompt 仍寫市場穩定與沒有飢荒，要改成什麼；反思報告要給政府哪些數字（目前包含達標與否、挨餓與死亡人數）
- **政府直接改變價格**：`price_cap` 會直接限制價格、`issue_currency` 會推高名目價格，這樣的價格要不要算均衡價格
- **飢荒與死亡**：不再是目標後，還要不要記錄成輔助指標。如果只看價格，政府可能靠徵糧或處決平民壓低需求，價格好看但社會已經出問題
- **天災強度**：目前強度與預警時間是隨機的，不同次天災的價格不能直接比，可能無法判斷「多次天災後的變化」是來自學習還是天災較輕；要固定強度，還是用同 seed 的 A 組校正
- **社會規則的實驗條件**：實驗分組表的社會規則都是「無」，但設計上又有規則與違規拒絕，正式實驗要用哪一版規則
- **數值**：平時的決策間隔 N、評估期長度、天災其他各段的長度、每組的 seed 數（暫定 5）
- **LLM**：供應商與模型 ID（正式實驗前鎖定）、temperature
- **政府行動的細節**：各行動的參數範圍、初始預算與儲備、每個行動對應的平民反應規則
- **B 組的「亂搞」怎麼量**：B 組沒有社會規則，政府的任何決策都不會被拒絕，所以引擎本身不會留下「違規」的紀錄。
  - 什麼樣的決策算「亂搞」？是看行動種類（例如處決、徵糧），還是看行動的程度（例如發行多少貨幣才算過頭）？
  - 判斷的標準要在跑實驗之前訂好，還是跑完再看決策內容決定？
  - 這個標準跟 C 組的社會規則是同一套，還是另外訂？
  - 要記錄成什麼形式？次數、比例，還是逐筆列出？
- **C 組的「意識到為何會成功」怎麼量**：目前分組表寫了這個目的，但還沒有對應的資料或指標。
  - 「意識到」要從哪裡看出來？政府的記憶內容、每次決策附的理由，還是反思時寫的內容？
  - 怎樣才算「正確」意識到？需要先列出每種天災下真正有效的做法嗎？
  - 由誰判讀？組員人工看、另一個 LLM 評分，還是用關鍵字等固定規則？
  - 如果政府成功了，但寫的理由是錯的，要怎麼算？
- **平時的市場會不會收斂**：研究目標是評估期內的均衡價格，前提是沒有天災時，市場會穩定在某個價格附近。
  - 現在的市價依淨需求調整，平常會不會一直震盪或持續上漲、下跌？
  - 要用什麼方式確認？例如跑沒有天災、沒有政府的模擬，看價格變化？
  - 如果平常就不收斂，要先調整引擎（市場、平民行為），還是改變均衡價格的定義？
  - 「收斂」的標準是什麼？價格變動小於多少、持續多少回合？
- **人口變化**：平民死亡後不會補回，吃糧的人變少，糧食需求下降，價格也會跟著變。
  - 後面幾次天災的價格變化，要怎麼分辨是政府學到了，還是人口變少？
  - 人口要不要恢復？如果要，是在恢復期補回原本的人數、讓平民自然出生，還是每次天災前重置整個世界？
  - 如果人口恢復，政府處決或讓平民餓死就幾乎沒有長期代價，這樣可以接受嗎？
  - 不同組的人口差異很大時，價格還能直接比較嗎？
- **政府看得到什麼**：政府的決策只能依據它看得到的資訊，給多少資訊會影響它的表現，也會影響各組之間的比較。
  - 政府的觀察要包含哪些？例如價格、自己的預算與儲備、死亡人數、挨餓人數、平民的庫存。
  - 要給個別平民的資料，還是只給整體統計（平均、總數）？
  - 平民的 persona 或遵守率要讓政府看到嗎？看到的話，政府是不是會變得太全知？
  - 天災的預報要給多準確？政府知不知道預報可能有誤差？
- **「遵守政府政策」的具體行為**：persona 裡有「會不會遵守政府政策」，但如果沒有定義不遵守時會做什麼，這個屬性就不會產生任何作用。
  - 對每一項政府行動，平民不遵守時分別會做什麼？例如：
    - `price_cap`：用超過上限的價格私下交易？乾脆不賣？
    - `collect_tax`：逃稅？少報收入？
    - `seize_food`：藏糧？反抗？
    - `publish_forecast`：不相信預報？還是照樣囤糧？
  - 遵守與否是每次擲骰決定，還是由 persona 數值直接決定？
  - 政府能不能知道誰沒有遵守？不遵守有沒有懲罰？
- **persona 的分布與變化**：gluttony 會直接增加糧食需求，sloth 會直接減少產量，兩者都會直接影響均衡價格。
  - 每個 persona 數值要怎麼分配給平民？固定比例、隨機分布，還是依特性（有無買賣、有無產出）決定？
  - 隨機的話，各組在同一個 seed 下要拿到一樣的平民嗎？
  - 原本的 `fairness`、`sociability`、`goal` 要保留還是刪掉？七宗罪裡其他幾項要不要加？
  - persona 是一開始就固定，還是會隨事件改變？例如被徵糧後還願不願意遵守、天災後會不會變得更貪心或更保守？
  - 如果會改變，要不要另外加「對政府的信任」之類的狀態，和固定的 persona 分開？

## 快速開始

需要 Python 3.11+。以下指令目前執行的是尚未加入政府的版本。

```bash
pip install -e ".[api,dev]"

# 單次模擬（紀錄寫到 runs/）
python -m civsim run --config configs/baseline.yaml

# 批次實驗：重複 5 個 seed，輸出 summary.csv
python -m civsim experiment configs/baseline.yaml --repeats 5

# 測試
python -m pytest
```

### 經由 API（digiRunner）執行

```bash
python -m civsim serve --config configs/baseline.yaml     
# 啟動 world-api，文件在 http://localhost:8000/docs
python -m civsim remote --base-url http://localhost:8000   
# Agent 端透過 HTTP 呼叫
```

接上 digiRunner 後，`--base-url` 改成 Gateway 位址（或設定 `.env` 的 `DIGIRUNNER_BASE_URL`），Agent 的每次呼叫就會經過 Gateway。PostgreSQL 與 digiRunner 用 `docker compose up` 啟動（digiRunner 設定待補）。

### 給前端使用的 API

| 路徑 | 內容 |
|---|---|
| `GET /world/state` | 目前回合、市場、每個 Agent 的狀態與權限 |
| `GET /world/metrics` | 每回合指標 |
| `GET /world/events?since_tick=N` | 第 N 回合之後的事件 |

前端開發伺服器的來源預設允許 `http://localhost:5173`，其他來源用環境變數 `CIVSIM_CORS_ORIGINS` 設定（逗號分隔）。

## 專案結構

```
src/civsim/
  models.py          核心資料結構（AgentState、Action、Observation、WorldState…）
  config.py          實驗設定（YAML）
  cli.py             命令列入口
  world/             模擬引擎：回合流程、行動驗證與結算、市場、世界事件（天災）
  policy/            模擬世界的權限與制度（舊方向，預定移除）
  agents/            Agent 決策：rule_based（平民）、llm（政府，待實作）
  api/               world-api（FastAPI），註冊在 digiRunner 後面
  gateway/           Agent 端經 Gateway 呼叫 world-api 的 client
  storage/           事件紀錄（JSONL；PostgreSQL 待實作）
  analysis/          指標：價格、挨餓與死亡人數、吉尼係數…
  experiments/       重複實驗與摘要
configs/             實驗條件設定檔（hierarchical、no_sharing 為舊方向的條件）
db/schema.sql        PostgreSQL schema
docs/architecture.md 架構與專案邊界
tests/
```
